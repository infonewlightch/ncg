# Interface localization

2026-09-24: NCG now retains the selected BCP 47 language/script for its interface, instead of coercing every language other than Korean, English and Spanish to English. Korean/English/Spanish ship with the app; generated packs for Portuguese, Simplified Chinese, Traditional Chinese, Thai, Arabic, Persian, Hindi and French also load on demand without a model request. Other written languages request automatic translations of the current page's known UI messages. This is a delivery mechanism, not a claim that all ISO entries (including sign languages) have verified translations.

- `src/i18n/source.json` is the developer-owned catalogue (768 messages). Browser requests contain only language, fixed batch number and catalogue revision. They cannot include user posts, chat, credentials or arbitrary text. Scripture and course content are not sent to this endpoint.
- `/api/interface-translation` uses the existing Netlify AI Gateway. It checks origin, JSON size, exact language/script, source revision, message IDs, order, placeholders/links, output size and completion status. The model must decline languages it cannot translate reliably. Sign languages cannot be represented as text UI translations and receive an explicit unavailable state. Generated translations are marked unreviewed and require native-speaker review.
- Cache keys include revision, model, language/script and batch. Validated results are shared in Netlify Blobs and saved on the device for reuse. Failed batches do not automatically retry or turn into a success state. Changing the language does not apply late results from the previous language.
- Requests are bounded: 24 fixed messages, model timeout 25 seconds, 6,000 output tokens, two browser requests and four model requests per process at once. Netlify rate limit: 80 requests per 180 seconds per IP/domain. UI generation has a separate shared Blobs counter of 300 uncached requests per UTC day. Conditional writes, failed PUT rejection and required read ETags protect the counter, but this is not a financial spending guarantee. Existing Bible/community PostgreSQL budgets are unchanged. No payment plan, auto-recharge, secret or database migration was changed.
- RTL script detection uses the selected BCP 47 script; desktop sidebar placement follows direction. Source Bible passages retain their edition language and direction.

Validation pending deployment: unit tests cover translation input boundaries, cache reuse, unsupported output, late-language responses, placeholders, script direction and concurrent budget claims. Production model delivery and native-language accuracy must be recorded separately after verification.

Production verification: Portuguese generated successfully for all 768 catalogue messages in 32 batches. Public browser menu, reader controls, status, page heading and persisted language confirmed in Portuguese. Generated Portuguese source is `src/i18n-generated/pt.json`, marked unreviewed; it is not a native-speaker reviewed translation. Public static asset SHA-256 matched the local production build.

Additional checks: live Arabic, French and Traditional Chinese (`zh-Hant`) navigation batches returned HTTP 200 in their requested script. Arabic public browser showed translated home and Bible controls with RTL desktop sidebar; a 390px mobile home in normal and large-text modes had document width 390px and no horizontal overflow. Portuguese Genesis 1 and 2 rendered the Biblica source, with 66 books and verse 1 selected after changing chapters. Final tests: 309 across 59 files; production build and 768-key catalogue check passed. These are delivery/layout tests, not expert linguistic or theological review. QT reflection guides and educational lesson bodies use their separately authored content translations and are not silently rewritten by the UI endpoint.
