# NCG 요청 제한과 호스팅 규칙

2026-09-24 운영 배포 `1dcf3a6`의 후처리 로그에서 `Too many rules defined, max for your account tier is 2`를 확인했습니다. 이때 사이트 배포는 성공했으나 기존 6개 함수의 네이티브 제한이 적용됐다고 볼 수 없습니다. 초과 시 일부만 적용되는지 전체가 거절되는지는 공식 설명으로 확정하지 못했습니다.

[Netlify 공식 설명](https://docs.netlify.com/manage/security/secure-access-to-sites/rate-limiting/)의 프로젝트당 코드 규칙 수는 Free/Starter/Personal 2개, Pro/일반 Enterprise 5개입니다. 따라서 유료 플랜 전환만으로 기존 6개 설정의 유효성이 보장되지 않습니다. 결제나 플랜 변경 없이 아래처럼 정리합니다.

## 유지하는 Netlify 네이티브 제한 2개

| API | IP·도메인 기준 제한 | 이유 |
|---|---|---|
| `/api/bible-source` | 60초 동안 120회 | 공개 성경 공급처 요청에는 별도 모델 일일 한도가 없음 |
| `/api/bible-translation` | 180초 동안 6회 | 익명 참고번역의 공유 예산 소진 방지 |

최종 적용 여부는 배포 후처리의 성공 기록으로 확인합니다. 기본 Netlify 플랫폼 보호와 별개인 사용자 설정 규칙입니다.

## 함수 내부의 보완 제한

| API | 동일 워커의 IP 기준 제한 |
|---|---|
| `/api/interface-translation` | 180초 동안 80회 |
| `/api/video-translation` | 180초 동안 40회 |
| `/api/translate` | 180초 동안 30회 |
| `/api/push-status` | 60초 동안 60회 |

`server/netlify-request-limits.ts`의 모듈 단위 카운터를 각 함수 입구에서 사용합니다. 저장소 조회·인증 조회·모델 호출 이전에 거절합니다. 클라이언트의 전달 헤더를 신뢰하지 않고 Netlify `context.ip`만 사용합니다. IP가 없거나 유효하지 않으면 하나의 보수적인 공용 버킷을 사용합니다. 함수별 버킷은 독립적이며 도메인 별칭을 바꿔도 새 IP 버킷을 만들지 않습니다.

만료 키를 정리하고, 활성 키 10,000개에 도달하면 기존 키를 퇴출하지 않고 신규 키를 거절합니다. 초과 응답은 `429`, 실제 남은 시간의 `Retry-After`, `Cache-Control: no-store`를 반환합니다. IP는 워커 메모리 안에서만 사용하며 로그나 외부 저장소에 기록하지 않습니다.

**이 제한은 분산된 전역 IP 한도와 같지 않습니다.** 워커가 증설·재시작되면 카운터가 나뉘거나 초기화됩니다. 기존 공유 모델 예산은 별도로 유지합니다: 성경·커뮤니티 각 60회/일, 커뮤니티 사용자·게스트별 20회/일, UI·영상 각각 300회/일. 예산은 신규 모델 생성 호출에 대한 한도이며 모든 호스팅 비용의 상한은 아닙니다. 전역 IP 단위 강제 제한이 추가로 필요하면 공유 저장소 기반 제한 또는 Edge 라우팅을 별도 검증해야 합니다.

## 검증

- 원래의 각 시간창과 한도를 유지하고 실제 함수 핸들러를 통해 임계치를 넘겨 429를 확인했습니다.
- 거절된 요청이 저장소·원문·번역 핸들러에 도달하지 않음, 전달 헤더 교체로 우회하지 못함을 검증했습니다.
- 시간창 만료 후 재개, 서로 다른 IP/기능 분리, 누락/위조 IP 보수 처리, 활성 키 포화 시 차단·만료 후 회복을 검증했습니다.
- 운영 사이트에 과도한 요청을 보내 차단을 유발하는 부하 테스트는 하지 않습니다. 배포 결과는 [운영 체크포인트](checkpoint-2026-09-24.md)에 기록합니다.
